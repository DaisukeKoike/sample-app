# 根拠のある課題起票
入力は `$ARGUMENTS` または利用者の説明。実装・修正は行わない。

## 1. 対象と重複を確認
- `git remote -v` と `gh repo view --json nameWithOwner` で対象を確認する。異なる場合は中止。
- `gh issue list --state all --limit 100 --search "<語> in:title,body"` と `gh pr list --state all --limit 100 --search "<語>"` を実行する。上限到達時は検索語を分け、全件確認済みとは言わない。
- 候補は `gh issue view <番号> --json title,body,comments,state` で読み、重複・再発・依存・関連なしを判断する。同一の未完了課題は新規作成せず追加情報をコメントする。

## 2. 調査と分類
- bug / enhancement / feedback を既存ラベルから選ぶ。改善・インフラは enhancement と本文の種別で区別する。
- コード、テスト、仕様、`git log -S '<識別子>' -- <path>` を確認する。
- 不具合は可能なら隔離した一時DBで再現し、入力、実行コマンド、期待値、実測値、再現頻度、コミットSHAを記録する。再現できなければ「未再現」。原因は確定/仮説/未調査を明示する。
- 機能要望では存在しない不具合や原因を作らず、利用者・目的・現状の制約・実現後の価値を整理する。
- 大きい要求は独立検証可能な単位に分け、親課題と子課題案を提示する。大量起票は利用者の指示範囲を確認する。

## 3. 本文と品質ゲート
[references/issue-template.md](references/issue-template.md) に従い本文を作る。
- 受入基準は AC-01 形式で識別し、Given/When/Then または入力と期待結果で書く。正常・異常・境界を含める。
- 「適切に動く」「テストする」だけの基準は禁止。再現できる値を使う。
- 対象外、画面/API/DB/インフラの影響、互換性、データ移行、テスト、リスク、切戻しを必要に応じて具体化する。不要な項目は理由付きで対象外とする。
- 優先度・見積りは提案と明記。担当者、期限、マイルストーンを捏造・自動決定しない。
- 秘密情報・実データを含めない。未確認事項を埋めるための推測は禁止。
- 状態遷移・複数層の処理・DB変更・複雑な分岐が絡む場合は `.claude/uml-guide.md` を読み、「設計図」節に mermaid 図を入れる。不要なら理由を1行書く。図を入れたら `python tools/check-mermaid.py issue-body.md` を実行する。
- `python tools/validate-issue.py issue-body.md` を実行し、不足を修正する。機械検証は内容の正しさを保証しないため、証拠と基準を読み直す。

## 4. 起票
`gh issue create --title "[種別] 対象と観測事象または価値" --body-file issue-body.md --label <既存ラベル>` を実行する。
成功時だけURL、種別、AC一覧、未確認事項、優先度案を報告する。失敗時は本文を保持して原因を報告する。成功後だけ一時本文を削除する。

## 演習の扱い
- 意図的なバグも通常の不具合と同じ証拠基準で起票する。
- 演習の正解集を最初から読み込まない。ヒントや答えを求められた場合のみ参照する。
- 起票ついでにコード変更、マージ、インフラ操作を行わない。
